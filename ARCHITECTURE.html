HappyMan POS

System architecture, deployment plan, and remaining work for v1 shipping by end of 2027.

Author: Devayani Senthilvelan Status: Living document · Updated June 2026

01 System Architecture

HappyMan POS is a local-first retail point-of-sale system for two sweet shops. Each shop runs independently with its own hardware and database. Sales work fully offline; only product price updates and (future) sales sync require internet.

Two independent shops · No internet required for daily operation · Cloud added in v1.5

Key architectural principles

Local-first design

Each shop's POS works without internet. The only requirement is a local WiFi router (no ISP plan needed) so the tablet and Pi can talk to each other. If the shop's internet goes down, sales continue normally.

Two independent databases

Each shop's Pi has its own SQLite file. Shop 1 doesn't know about Shop 2 and vice versa. Combined reporting requires manual Excel export from each shop (v1) or cloud sync (v1.5).

Single source of truth per shop

The Pi's SQLite database is authoritative. The tablet's localStorage is a cache for UI speed only, never the source of truth. Sales are not "saved" until the Pi confirms.

Tablet is a thin client

The tablet runs only a web browser. All Python, all SQL, all business logic lives on the Pi. The tablet can be swapped out anytime without losing data — only the Pi matters.

02 The Sale Flow

This is what happens for every sale, in order. Understanding this flow is essential — every bug we've debugged maps to one of these steps failing silently.

Each step can fail · Verify the data, not the UI
⚠ Important — silent failure risk

If step 4 fails (Pi unreachable), the current code still shows success on the tablet because localStorage already saved (step 3). Staff sees a green checkmark even though the database never got the sale. This is why a "backend status indicator" is on the todo list below.

03 Data Model

The SQLite database has four core tables. Sales and sale_items are append-only (never updated, never deleted). Products and categories can be updated when prices or product lists change.

Four tables · Standard relational normalization · Identical schema in both shops

05 Future Roadmap

What comes after v1 ships. These are intentionally not blockers for shipping v1 — they're planned but deferred.

v1.5 Cloud sync

Single source of truth for products

Estimated · 3-4 weeks · After v1 stabilizes

Add a cloud database (Supabase recommended). Each shop's Pi fetches products from the cloud on startup, with a manual "Sync now" button for mid-day price updates. Sales sync from each shop up to the cloud nightly. Each shop still works offline between syncs.

Why it matters: Eliminates manual duplicate product updates across two shops. Frequent price changes (sugar, ghee, festival pricing) become a single edit. Plus enables real consolidated reporting.

v2 Stock tool

Manufacturing & distribution tracking

Estimated · 4-6 weeks · After v1.5

A simple web app for the manufacturing area where parents record what was made and what was distributed to each shop. Mobile-friendly (parents use their phone). One form, one list, one summary. Data stays separate from POS for now; can be joined in reports later.

Why it matters: Parents (educated, motivated) learn the digital workflow first. They become internal champions who can train shop staff later. Lowers the adoption risk for the POS rollout.

v2.5 Dashboards

Sales analytics & comparisons

Estimated · 6-8 weeks · After v2

Read-only web dashboard that runs SQL queries against the cloud database. Real business questions: revenue per shop, top products by week, peak hours, average ticket size, stock-to-sales ratio per item. This is the portfolio centerpiece for data analyst job applications.

Why it matters: Turns the POS from "record-keeper" into "decision tool." Also the most career-relevant piece — every SQL query is portfolio evidence.

v3 Expenses

Expense entry for parents

Estimated · 3-4 weeks · After v2.5

Mobile-friendly form for parents to log expenses (salaries, purchases, utilities, rent). Categorized. Feeds into the dashboard so profit calculations become possible.

Why it matters: Until expenses are tracked, "profit" is a guess. Completes the financial picture.

v3.5 Polish

Auto-update, packaging, refinement

Estimated · 4-6 weeks · End of 2027

Pi auto-updates via git pull on a schedule, or Windows .exe via PyInstaller if shop migrates to PCs. Final bug fixes from accumulated production usage. Any features identified by real staff feedback.

Why it matters: Maintenance burden goes down. System runs itself.

06 Key Decisions Log

Choices made along the way. Documented so future-you knows why things are the way they are.

Decision Why Revisit when
SQLite for sales storage in v1 Career-relevant SQL practice. Future-proof to bigger DBs. When sales > 1M rows (years away)
Two-table schema (sales + sale_items) Normalized relational design. Enables analytical queries. Never — this is correct.
localStorage as UI cache only Fast UI, durable Pi database, clear separation. Never — this is correct.
Bill numbers: continuous, shop-prefixed (HM1-1043) GST-future-proof. No daily resets. Unique across shops. Never — this is correct.
v1: each shop independent, no cloud sync Ship faster. No internet dependency for daily operations. v1.5 — after both shops stable in production.
Pi + tablet, not Windows tablet or touch PC Cheapest way to validate before shop renovation. ~₹6-10k vs ₹50k. After 2-3 months of real shop usage.
Tamil-English bilingual UI throughout Staff speaks Tamil; customers see English prices. Never — this is correct.
POS as portfolio piece, not as a commercial product Career path is data analyst job, not freelance dev. After landing first analyst job (2027+).
camelCase in JS, snake_case in Python/SQL Each language's convention. Transform at the API boundary. v1.5 standardization pass.
Network: testing requires phone hotspot at home Telstra apartment WiFi has client isolation enabled. Not relevant in production shop (different network).
